# 需求确认与执行交接

把需求处理分成“对齐”和“交接”两个阶段。确认前只调查、分析和讨论，不实施需求；确认后输出自包含的执行指令，仍不在当前会话实施。

## 核心规则

- 先理解再设计。必要时只读检查仓库、现有实现、依赖和测试，避免让用户回答能从代码中查到的问题。
- 根据任务规模控制深度。简单改动可以简短，但不得跳过目标、边界、主要风险和验收方式。
- 分批提出影响决策的少量问题，优先解决会改变范围、架构、用户体验或数据行为的问题，避免一次倾倒通用问题清单。
- 明确区分“用户已确认”“从仓库验证”“建议”“暂定假设”和“尚未决定”。不得把推测写成既定事实。
- 给出推荐设计及理由。存在实质性替代方案时，说明各方案的收益、代价和选择条件；不存在有意义的替代方案时，不人为制造选项。
- 不承诺穷尽所有风险。列出已识别风险、缓解措施和仍可能存在的未知项。
- 在用户明确表达“确认”“同意”“按这个方案”或等价批准前，不输出最终执行指令，不修改代码，不启动实现型子任务。
- 用户修改任何关键决定后，更新方案并重新请求确认。不得沿用已经过期的批准。
- 除非用户明确要求跳过本流程并立即执行，否则不得自行绕过确认门槛。

## 第一阶段：调查与对齐

### 1. 建立需求模型

从用户描述和仓库事实中整理：

- 要解决的问题、期望结果和受益对象
- 包含范围、明确不做的内容和可能受影响的模块
- 行为、界面、数据、兼容性、性能、安全、时间或技术约束
- 与现有行为的差异，以及迁移、回滚或降级要求
- 可观察、可验证的完成标准

若信息不足，先说明当前理解，再询问最关键的缺口。不要因为细枝末节阻塞整体对齐；可逆且低风险的细节可以提出默认值，并标记为待确认假设。

### 2. 检查适用风险

只检查与任务相关的项目：

- 功能正确性、异常路径、边界输入和状态一致性
- API、配置、文件格式、持久化数据和向后兼容性
- 并发、异步、生命周期、资源释放和失败恢复
- 安全、隐私、权限、敏感信息和不可信输入
- 性能、内存、启动时间和大数据量行为
- UI 交互、焦点、键盘操作、可访问性和空/载入/错误状态
- 测试可复现性、可观测性、发布、迁移、回滚和维护成本
- 与未提交改动、现有架构、依赖版本和项目规范的冲突

为每个重要风险说明发生条件、影响、缓解方式和验证办法。没有证据的风险使用“可能”表述。

### 3. 形成设计

给出与现有代码风格一致、改动范围最小且能满足目标的推荐方案。至少明确：

- 关键流程、状态或数据如何变化
- 预计修改的模块、职责边界和接口
- 错误处理、兼容与回滚策略
- 测试层级、关键用例和执行的质量检查
- 明确不做的过度设计或顺手重构

如果仓库事实不足以支持设计，先进行只读调查。若仍无法消除会显著改变方案的不确定性，将其作为阻塞问题交给用户决定。

### 4. 提交确认摘要

使用紧凑结构向用户汇总：

1. 当前目标与范围
2. 推荐设计及关键取舍
3. 已识别风险与缓解措施
4. 验收标准与验证计划
5. 已确认决定、暂定假设和仍待决定项

存在待决定项时，提出具体问题并继续对齐；不存在时，请求用户明确确认整个方案。此时不要附带可执行提示词，以免未经确认的草案被误用。

## 第二阶段：生成交接指令

仅在整个方案获得明确批准后，输出一个 Markdown 代码块中的独立指令。指令必须让一个看不到当前对话的新智能体也能安全执行，不使用“如上”“之前讨论过”等上下文引用。

交接指令按任务需要包含：

```text
你将在 <仓库/工作目录> 中完成以下任务。

目标
- <最终可观察结果>

背景与仓库事实
- <新会话理解任务所需的事实、路径、符号和现有行为>

范围
- 必须完成：<内容>
- 不在范围：<内容>

已确认设计
- <关键流程、状态、数据、接口和职责边界>
- <错误处理、兼容、迁移或回滚策略>

约束与项目规范
- <技术、产品和过程约束>
- 先检查适用的 AGENTS.md 和技能说明；保留无关的用户改动。

风险与防护
- <风险、触发条件、缓解措施>

实施要求
- <必要步骤与允许智能体自行判断的部分>
- 仅修改与需求直接相关的内容，不进行无关重构。

验收标准
- <逐条可验证条件>

验证
- <应新增或更新的测试>
- <应运行的具体检查；无法运行时说明原因和替代证据>

交付
- 完成实现与验证，并总结改动文件、行为变化、测试结果及剩余风险。
```

生成前复核指令：

- 纳入所有已确认决定，不包含已被否决或过期的方案。
- 不把暂定假设伪装成确认事实；若仍有阻塞问题，返回第一阶段而不是交接。
- 给出足够上下文和验收标准，但不要要求执行者机械照搬可能已过时的行号或实现细节。
- 对无法预先确定的低风险实现细节，明确授权执行者基于仓库现状做最小合理选择并记录决定。
- 不在交接指令中要求执行者再次进行产品决策；若确实需要用户决策，说明当前尚不能交接。

## 输出风格

- 使用用户使用的语言；Vektra 项目默认使用中文沟通。
- 先给结论，再给必要依据。
- 保持问题、风险和方案具体到当前需求，避免空泛模板话术。
- 可以持续多轮对齐；每轮只重复发生变化或仍需确认的内容。
