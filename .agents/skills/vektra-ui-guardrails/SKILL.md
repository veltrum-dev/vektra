# Vektra UI 设计约束

Vektra 是独立、易组合的纯 GPUI 组件库，不是应用框架；不要假设存在 Vektra Root、Provider 或强制初始化流程。Vektra 负责自身组件的结构、状态、交互和主题行为；宿主应用负责全局快捷键体系、菜单文档、业务任务进度、大型项目上下文和全局窗口管理。

涉及 GPUI API、Rust 代码或 GPUI 测试时，同时使用仓库中的 `gpui`、`rust-code-style` 或 `gpui-test` skill。开始前检查现有组件、主题 token、锁定 GPUI revision 和真实 API，优先复用仓库已有模式，避免无关重构和猜测性抽象。

## 使用流程

1. 识别当前任务适用的硬规则、条件规则和宿主应用责任。
2. 检查现有组件、尺寸、variant、状态模型、主题 token 和相关测试结构。
3. 说明新增视觉语义、状态或 API 是否必要；新增 variant 必须表达稳定产品语义。
4. 设计或实现时保持组件边界清晰，不把宿主应用职责写成 Vektra 组件保证。
5. 完成后按检查类别报告“通过 / 不适用 / 未验证”，并给出证据；没有运行的平台、性能或视觉检查必须标记为“未验证”。

## 设计语言

硬规则：

- 颜色、间距、尺寸、字号、圆角、边框和阴影优先来自 DTCG/Vektra 语义 token。
- 不得为单个组件或页面创造与现有体系平行的视觉语言。
- 优先复用已有组件、尺寸、variant 和状态模型。
- 新增 variant 必须表达稳定产品语义，不能只是临时颜色或局部页面差异。
- 默认不新增任意背景色、圆角、边距、内边距等自由样式 API。
- 必须提供自定义能力时，不能破坏主题、焦点、禁用、可访问性和组件基本结构。
- 每个交互组件必须定义适用的完整状态矩阵：`normal`、`hover`、`pressed`、`focus-visible`、`disabled`，以及组件需要的 `selected`、`loading`、`error` 等状态。
- 不适用的状态要明确说明，不能静默遗漏。
- 优先使用语义属性表达意图，避免让调用方直接拼装底层视觉细节。

## 无障碍与人体工程学

硬规则：

- 所有交互组件都必须支持其语义对应的键盘操作。
- 鼠标和键盘激活应进入相同业务回调或状态转换。
- 必须提供正确的 Role、可访问名称、焦点顺序和清晰的 `focus-visible`。
- `disabled` 状态必须同时阻止鼠标和键盘激活。
- 纯图标交互必须有可访问名称。
- `hover`、`pressed`、`focus-visible` 和 `disabled` 必须清晰且跨组件一致。
- 不能只通过颜色表达关键状态。

条件规则：

- 组件暴露快捷键时，Tooltip、Menu 或可见提示应能展示快捷键信息。
- 提供拖动、上下文菜单、调整大小或滚动时，必须验证对应鼠标交互、边界和失败路径。
- 复合组件根据语义实现方向键、Home、End、Escape、Enter 或 Space。
- 输入组件必须验证输入法、组合输入、焦点和文本选择行为。

宿主应用责任：

- 全局快捷键是否完整。
- 快捷键文档和应用级菜单是否齐全。
- 跨页面的完整键盘导航和应用级焦点恢复。

## 主题与响应式

硬规则：

- 所有组件及其状态必须在 Light、Dark 和 System 模式下使用正确的语义 token。
- 不得在组件渲染代码中随意硬编码主题颜色。
- 叶子组件在窄约束下不得异常溢出；文本应根据语义选择截断、换行或缩放。
- 使用 GPUI 逻辑尺寸和矢量资源，不依赖固定设备像素或单一 DPI。

条件规则：

- 容器和复合组件必须验证窄窗格、短面板及窗口调整大小。
- Dialog、Modal、Menu、Popover 等浮层存在时，必须保持在视口内，并在尺寸不足时提供滚动、压缩或重新定位策略。
- 普通 Button、Icon 等叶子组件不需要伪造对话框或短面板测试，只验证自身约束行为。

## 平台一致性

硬规则：

- 公共 Vektra 组件以 Windows、Linux 和 macOS 可移植为目标。
- 优先依赖 GPUI 的跨平台 API。
- 平台特殊逻辑必须隔离并说明原因。
- 组件不得无理由覆盖系统字体、缩放、窗口外观或输入法行为。
- 没有实际 CI、构建或人工验证证据时，平台状态必须写成“未验证”，不能声称“完全可用”。

## 交互反馈与性能

硬规则：

- 所有用户交互必须立即产生可观察反馈。
- 渲染路径中不得进行阻塞 I/O、文件读取、JSON 解析、主题完整转换、正则编译或其他明显的重复重工作。
- 普通叶子组件不承担“大型文件/大型项目性能”责任。

条件规则：

- 长任务由宿主应用决定何时开始，但 Vektra 组件应能表达 `loading`、`pending`、`progress`、`disabled` 或 `cancel` 等适用状态。
- List、Table、Tree、虚拟滚动或大型集合组件必须验证大数据量行为、复用和虚拟化策略。
- 120fps 的完整帧预算约为 8.33ms。Vektra 可以把 8ms 作为明确基准环境下的性能目标，但不得将其写成所有组件、所有机器和完整宿主应用的无条件保证。
- 性能敏感组件需要提供具体基准、数据规模和环境；没有测量时标记为“未验证”。

## 测试目录结构

每个 crate 采用以下结构：

```text
crates/<crate>/src/
crates/<crate>/tests/*.rs
crates/<crate>/tests/unit/*.rs
crates/<crate>/tests/support/
```

- `src/` 只放生产代码和最小测试模块声明。
- `tests/*.rs` 放基于公共 API 的集成、交互和行为测试。
- `tests/unit/*.rs` 放必须访问私有实现的单元测试。
- `tests/support/` 放测试 fixture、模拟 renderer、辅助 View 和共享工具。
- 禁止在 `src/**/*.rs` 中直接编写完整的 `#[cfg(test)] mod tests { ... }`。
- 禁止把测试 fixture、模拟对象、测试 View 或 renderer 混入生产源码。
- 公共行为优先通过 crate 的公共 API 在 `tests/` 中验证。
- 不得为了集成测试扩大生产 API 的可见性。
- 私有逻辑确实需要白盒测试时，允许生产文件只保留最小声明：

```rust
#[cfg(test)]
#[path = "../tests/unit/button.rs"]
mod tests;
```

- `#[path]` 路径必须根据实际源文件位置正确计算。
- `tests/unit/` 中的测试通过上述模块声明获得私有访问，不应被 Cargo 误作为独立集成测试入口。
- 新增或修改的测试必须遵守此结构。
- 现有内联测试视为遗留债务；当前任务不迁移它们，也不顺手修改业务代码。
- 后续不得继续向遗留内联测试模块添加测试。
- 如果未来任务需要修改某个现有内联测试模块，应在该任务中把受影响模块的测试迁移到对应 `tests/` 目录。
- 测试文件名称应对应被测组件或行为。
- GPUI 测试仍须遵守 `gpui-test` skill 的确定性调度、测试上下文和种子复现规则。

## 完成报告

按以下类别逐项报告“通过 / 不适用 / 未验证”，并给出具体证据：

- 设计语言
- 无障碍与键盘
- 鼠标交互
- Light/Dark/System
- 窄窗格、短面板和高 DPI
- 跨平台
- 即时反馈与长任务状态
- 性能
- 测试目录结构

不要把未运行的平台、视觉或性能检查写成通过。无法验证时说明缺少的环境、命令、平台或基准。
